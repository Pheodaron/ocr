# Проверка сравнения OCR — 2026-10-22

Управляемое Linux-окружение, Python 3.12; CPU quota 2, RAM 8 GiB, без GPU.
Podman/mise здесь не установлены; контейнерная проверка — Docker/Compose.

Проверено:

- `pytest -q`: **43 passed, 11 skipped**. Пропущены явно включаемые тесты настоящих
  моделей (Paddle и 10 генеративных backend). Обычные тесты не измеряют OCR-качество.
- Ruff lint/format, `node --check`, `git diff --check`.
- `uv.lock`: разрешены CPU-зависимости; Nemotron отделён от KDL/Falcon из-за
  разных версий PyTorch/Transformers.
- Compose-конфигурация всех 11 профилей; у каждого собственные worker и models-init.
- Сборки targets `api`, `vlm`, `paddle`, `kdl`, `jina`, `falcon`, `nemotron`.
  Jina действительно компилирует отдельный бинарник с RoPE-поправкой.
- Nemotron: импорт torch 2.11.0+cpu / torchvision 0.26.0+cpu / timm 1.0.22 и
  AutoModel/AutoProcessor внутри контейнера `--network none`, CUDA недоступна.
- Paddle: импорт PaddlePaddle 3.2.2 и PPStructureV3 в контейнере без сети,
  `is_compiled_with_cuda() == False`.
- Falcon/KDL: PyTorch 2.7.1+cpu импортируется в контейнере без сети; KDL
  импортирует Qwen2VLForConditionalGeneration; Falcon импортирует CPU attention
  и requests. CUDA недоступна.
- API через Compose доступен с хоста на localhost:8000, клиент отдаётся;
  `/api/config` содержит 11 моделей. Загрузка трёхстраничного PDF в сравнение
  GLM/dots/Nemotron вернула HTTP 202 и три задания.
- GLM-сервис без весов пометил только собственное задание failed;
  dots/Nemotron сохранились queued. GLM остался работоспособен для следующих заданий.
  Затем сервис GLM остановлен, dots запущен отдельно.
- Тесты проверяют фильтрацию claim/recover по backend, миграцию прежней SQLite,
  атомарную публикацию сравнения и одинаковые байты PDF, продолжение после ошибки
  страницы, ограничение повторов, сохранение первого успешного прохода.
- Проверены контракты локального multimodal HTTP и Nemotron CPU processor/generate,
  адаптеры форматов, HTML/Markdown-таблицы, ведущие нули, пустые ячейки и OTSL.
  Falcon CPU attention сравнивается с PyTorch SDPA, включая image-prefix/decode masks;
  interleaved squared-ReLU gate проверяется отдельно.

Ограничения:

`huggingface.co`/хосты весов Hugging Face и официальный Paddle BOS заблокированы
сетевой политикой окружения (HTTPS CONNECT 403). Настоящие веса не загружены.
Полный inference, CPU-совместимость custom checkpoint-кода, качество русского
текста/таблиц, пиковая RAM и ток/с **не подтверждены**. Особенно важна проверка
CPU-порта Falcon и нового Transformers runtime Nemotron. Сборка/импорты и mock
контракты не заменяют прогон настоящих моделей.

Для реальной проверки подготовьте веса выбранного профиля и запустите opt-in:

```sh
OCR_RUN_MODEL_TESTS=1 OCR_REAL_BACKENDS=glm_ocr,surya \
  uv run --frozen pytest tests/test_real_vlm.py -v
```

Для Falcon нужны `--extra falcon`, для KDL `--extra kdl`, для Nemotron отдельное
окружение с `--extra nemotron`; для llama.cpp локально нужен соответствующий
CPU-бинарник (Jina — с поправкой). Проще запускать через готовые Compose targets.
Проверка является smoke test, для сравнения точности нужен размеченный набор.

Временный Compose-проект `ocr-compare-verify` и его тестовые тома удалены.


## Регрессия: скрытая загрузка PP-Chart2Table

В PaddleX 3.3.13 `inintial_predictor` безусловно создаёт chart predictor,
даже при `use_chart_recognition=False`. Прежняя проверка итогового YAML этого
не выявляла. Новый тест вызывает настоящий конструктор PaddleOCR/PaddleX,
подменяя только низкоуровневые весовые предикторы. До исправления тест падал
на попытке создать `PP-Chart2Table` с `model_dir=None`; после исправления
инициализация запрашивает только девять подготовленных моделей.

В процессе документа factory временно пропускает выключенный chart predictor
и допускает остальные модели только из явных локальных каталогов. Защита
действует при конструировании и во время predict, включая ленивые модели;
после выхода, в том числе с исключением, исходная factory восстанавливается.
Проверены резервный OCR таблиц и конфигурация ориентации таблиц.
Это проверка реальной оркестрации библиотеки, а не inference на настоящих весах.


## Регрессия: dots.mocr Q5_K_M / BF16 возвращали HTTP 404

Прежний общий revision dots `fc5b04f...` содержал только Q8 decoder и Q8 projector.
Q5_K_M и BF16 добавлены позднее; теперь они используют полный commit
`8bc6c189780084cf59b10d55fadcbe7d1292696a`, а Q8 сохраняет прежний revision.
Наличие файлов проверено по деревьям обоих commit на Hugging Face, SHA256 Q5
сверена с LFS pointer в commit добавления файла. Добавлен regression test
со списками опубликованных файлов для трёх вариантов и тест ошибки HTTP 404:
в сообщении есть точный URL, временный файл удаляется, manifest не публикуется.
Полная загрузка гигабайтных файлов в этом окружении не проверена.


## Сборка контейнера без изолированной упаковки приложения

Все контейнерные `uv sync` используют `--no-install-project`. Приложение
запускается из `/app/src` через общий launcher `ocr-service`; собственный wheel
и Hatchling не требуются. Основные зависимости устанавливаются до копирования
исходников; проверка TLS сохранена, включены системные CA для uv.
Локальная установка проекта через mise/uv продолжает использовать pyproject.

Пересобран API-образ; в контейнере без сети проверены отсутствие Hatchling и
установленного distribution приложения, CLI, статические ресурсы, OpenAPI,
HTTP 202 на PDF и импорт приложения дочерним OCR-процессом. Без весов дочернее
задание штатно завершилось явной ошибкой manifest, а не ошибкой импорта.
Это исправление устраняет лишнюю загрузку build backend для приложения,
но не исправляет внешний обрыв TLS на PyPI при загрузке других зависимостей.


## Восстановление llama-server после сбоя страницы

53 теста прошли, 11 тестов настоящих весов пропущены. Контрактный тест локального
HTTP-сервера воспроизводит SIGABRT/обрыв соединения на второй странице PDF:
первая completed, вторая failed без 350-DPI повтора, третья completed после
перезапуска. В ошибке есть сигнал, текущая assert-строка и путь к журналу;
строки предыдущего документа исключены. Проверен предел восстановления:
если перезапуск не состоялся, новые попытки загрузки на каждой оставшейся
странице не выполняются. Реальную причину падения на пользовательском хосте
эти тесты не устанавливают — нужны журнал native runtime и cgroup/host события.


## Ограничение изображения для CPU VLM после подтверждённого OOM

В пользовательском контейнере dots.mocr `memory.max=max`, `oom_kill=1`:
подтверждено OOM-убийство; модель загрузилась, но первый запрос не завершился.
Добавлен лимит входа llama.cpp 1 500 000 пикселей. Рендер/preview остаётся
исходным. Тесты проверяют бюджет пикселей, пропорции, BGR→RGB без искажения
цвета, отсутствие увеличения небольших изображений и сохранение bbox
относительно исходного preview. Параметр входит в snapshot задания; actual
input dimensions попадают в метрики/raw и предупреждение страницы.
Пиковая RAM/качество после изменения на настоящих весах здесь не измерены:
это ещё нужно проверить на пользовательском документе.

## Остановка распознавания и удаление заданий

81 тест прошёл, 11 проверок настоящих моделей пропущены. В новых проверках
используются реальный worker, отдельная OS session и дочерний inference-процесс
с подпроцессом; только само распознавание заменено тестовой программой.
Подтверждены остановка группы процессов, освобождение очереди для следующего
PDF и сохранение уже готовой страницы. Проверены потеря координатора через
SIGKILL, освобождение блокировки, отмена оставшегося задания без worker,
сохранение запроса остановки при recover и его завершение после старта worker.

API-тесты покрывают отмену очереди, защиту отменённой страницы от поздней
записи, выгрузки сохранённых результатов, удаление при каждом статусе,
каскадное удаление страниц SQLite и файлов, сохранение hard link у другого
прогона сравнения. Старый ошибочный результат удаляется сразу, даже когда
блокировка backend занята другим документом.

В Chromium через Playwright и настоящий API проверены кнопки остановки и
удаления в истории/карточке/сравнении, выгрузка остановленного задания,
удаление ошибочного результата, обновление после удаления и очистка
localStorage открытой записи. Ошибок JavaScript не зарегистрировано.

## Генерация при пустом content — 2026-10-23

Проверены HTTP-контракты dots.mocr, GLM и обеих моделей LightOn: сервер
получает `--skip-chat-parsing`, запрос отключает выделение reasoning/tools
и thinking в шаблоне. Метаданные фиксируют выбранный режим.
Адаптер принимает текстовые части content, сохраняет исходный ответ и
восстанавливает только явный dots layout из reasoning с предупреждением.
Неполный JSON и произвольные рассуждения не становятся текстом OCR.

Проверены сохранение ведущих нулей в таблицах, диагностическая ошибка
пустого ответа без текста документа в сообщении и продолжение следующих
страниц для dots.mocr и LightOnOCR-3-0.8B. Исходный JSON ошибочной страницы
остаётся на диске. Реальное распознавание этими весами не проверялось:
в предоставленных пользователем данных нет HTTP body неудачного запроса,
поэтому причина именно этого запуска не подтверждена.

Отдельный C++ smoke test использовал настоящий парсер закреплённого
llama.cpp `47a3966` и его шаблон Qwen3.5. Для тестового OCR-ответа без
закрывающего thinking-тега прежний режим вернул `content_chars=0` и
`reasoning_chars=76`; новый режим pure content + thinking=false вернул
`content_chars=76` и `reasoning_chars=0`, сохранив строку побайтно.
Это проверка механизма парсера без весов, не inference LightOnOCR.

## LightOn Q5 и раздельные потоки — 2026-10-23

В изолированной копии изменений: 98 тестов прошли, 11 тестов настоящих моделей
пропущены. Ruff lint/format и проверка diff прошли. HTTP-контракт проверяет
разные `--threads=8` и `--threads-batch=16` и соответствующие метаданные.

Для обеих LightOn проверены Q5 decoder с pinned SHA256 и собственным Q8 vision,
загрузка только недостающего decoder, сохранение Q8-файлов и manifest, работа
обоих вариантов без сети после подготовки, точность отображения квантизации.
Проверены snapshot нового задания и восстановление Q8/прежних потоков для
старых заданий после смены конфигурации worker.

Compose обоих профилей проверен с Q5 и потоками 8/16: одинаковые настройки
получают API, загрузчик и worker. Worker сохраняет `network_mode=none`,
загрузчик не получает том документов. Podman в среде не установлен;
конфигурация проверена Docker Compose. Скорость и качество настоящего
LightOn Q5 на пользовательском i9-11900 не измерены.
