# Техническое задание: подготовка данных и дообучение распознавания документов

## 1. Цель

Разработать одно приложение с единым браузерным интерфейсом для подготовки, проверки и использования данных при дообучении распознавания документов.

Основная предметная область — сложные таблицы на русском языке: объединённые ячейки, многоуровневые заголовки, таблицы без рамок, плотные строки, многострочный текст, числовые значения и некачественные сканы.

Полный цикл работы:

```text
Проект и исходные документы
→ распознавание LightOnOCR-3-4B
→ независимое распознавание Qwen3.8-27B
→ автоматическое сравнение
→ ручная проверка и исправление
→ распределение документов по выборкам
→ создание версии набора данных
→ дообучение LightOnOCR-3-0.8B
→ оценка качества
→ пробное распознавание выбранной контрольной точкой
→ экспорт модели для применения на CPU
```

Приложение должно сохранять происхождение результатов и обеспечивать воспроизводимость подготовки данных, обучения и оценки.

Это единый инструмент управления всем процессом обучения. Автоматическая оценка полученных моделей на тестовом наборе и сравнение с исходной моделью входят в обязательные функции. Пользователь также может по желанию распознать собственный новый документ и проверить результат глазами. Не отделять оценку модели в самостоятельную систему или необязательную исследовательскую работу.

Здесь автоматическая оценка означает программный расчёт показателей после команды пользователя. Она не означает автоматический переход между этапами. Валидация внутри запущенного обучения выполняется по предварительно выбранной конфигурации; самостоятельный итоговый тест запускает пользователь.

## 2. Назначение моделей

| Модель | Назначение | Изменение весов |
| --- | --- | --- |
| **LightOnOCR-3-4B** | Первичное распознавание, получение текста, таблиц, блоков и координат | Не выполняется |
| **Qwen3.8-27B с визуальным модулем** | Независимое распознавание и выявление расхождений | Не выполняется |
| **LightOnOCR-3-0.8B** | Дообучение, оценка и последующее применение | Выполняется |

Все обучающие запуски, адаптеры LoRA, контрольные точки и экспортируемые обученные модели относятся **исключительно к LightOnOCR-3-0.8B**.

Перед реализацией проверить точные идентификаторы, версии и файлы моделей, их архитектуру и поддержку выбранными средствами исполнения. Обозначение Qwen предоставлено владельцем системы; нельзя молча заменять её другой моделью. Пути к весам и визуальным модулям задаются конфигурацией. Неподтверждённую совместимость явно отражать в документации и состоянии службы.

Qwen3.8-27B запускается отдельным контейнером **llama.cpp с поддержкой CUDA**. Приложение подключается к его совместимому с OpenAI HTTP API. Выбрать наиболее качественный подходящий вариант семейства **Q3**, совместимый визуальный модуль `mmproj` и небольшой контекст: модель, визуальный модуль, состояния и рабочие буферы должны одновременно помещаться в **16 ГБ видеопамяти**. Перенос вычисления слоёв или визуального модуля на CPU ради вместимости запрещён. Служебная работа процесса с оперативной памятью не считается таким переносом.

Начальный проверяемый профиль — одна последовательность и общий контекст 8192 токена; окончательный размер фиксируется после измерений. Контекст включает инструкцию, визуальные токены и ответ. Страницы PDF передавать последовательно отдельными запросами, не помещать весь документ в одну беседу. Не объявлять универсально лучшей квантизацию только по её названию: зафиксировать источник, ревизию, точные файлы и проверить сохранение русских чисел и структуры таблиц на характерных примерах.

До массовой обработки проверить полный ответ на плотной странице с выбранным контекстом, подтвердить размещение модели и визуального модуля на GPU по журналу llama.cpp и измерить пиковую видеопамять. Не считать вместимость подтверждённой только по размеру GGUF. Неудачная проверка блокирует только этап Qwen; автоматически заменять модель, переносить веса на CPU, обрезать ответ или ухудшать входное изображение запрещено. Если запрос превышает доступный контекст, явно сообщать причину.

### 2.1. Начальная конфигурация Qwen для проверки

Первый кандидат — [unsloth/Qwen3.8-27B-GGUF](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF): `Qwen3.8-27B-UD-Q3_K_XL.gguf` и `mmproj-F16.gguf` из того же репозитория. Приблизительные размеры — 13,1 ГБ и 0,93 ГБ; это размеры файлов, а не измеренный расход видеопамяти. Зафиксировать ревизию, контрольные суммы и точные размеры перед загрузкой. Название динамической квантизации не является доказательством её преимущества на русских таблицах.

Для зафиксированной версии llama.cpp проверить поддержку следующего профиля:

```text
llama-server
  --model /models/qwen/Qwen3.8-27B-UD-Q3_K_XL.gguf
  --mmproj /models/qwen/mmproj-F16.gguf
  --gpu-layers all
  --mmproj-offload
  --kv-offload
  --fit off
  --ctx-size 8192
  --parallel 1
  --flash-attn on
  --slots
  --host 0.0.0.0
  --port 8080
```

Это перечень аргументов для Compose, а не готовая многострочная команда оболочки. Образ должен иметь поддержку CUDA и RTX 5060 Ti; доступ к GPU передаётся Podman через CDI. `app` обращается к `http://qwen:8080/v1`. Не публиковать этот порт в интернет.

Для независимой транскрипции передавать `chat_template_kwargs: {"enable_thinking": false}`. Хранить полное исходное тело ответа и фактические параметры запроса до извлечения текста. Отключение рассуждений не заменяет проверку наличия полного содержательного ответа и завершения таблиц.

`--fit off` исключает автоматическую подгонку размещения; все слои и визуальный модуль должны действительно загружаться на GPU. Проверка `/health` и наличие аргумента `--gpu-layers all` сами по себе недостаточны: при недоступной GPU llama.cpp может проигнорировать аргумент с предупреждением. Требовать проверку журнала размещения и успешную обработку изображения. При нехватке памяти профиль не считать готовым; варианты Q3, контекста и рабочих буферов подбирать явно, без скрытого переноса на CPU или ухудшения изображения.

Первичные источники: [файл модели](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/blob/main/Qwen3.8-27B-UD-Q3_K_XL.gguf), [визуальный модуль](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/blob/main/mmproj-F16.gguf), [параметры llama-server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Для сравнения качества при достаточном запасе памяти доступны [варианты Bartowski Q3_K_M и Q3_K_L](https://huggingface.co/bartowski/Qwen3.8-27B-GGUF); увеличение файла не считать доказательством лучшего OCR без проверки.

## 3. Оборудование и программное окружение

- Операционная система — Linux.
- Контейнеры — Podman, запуск через `podman compose`.
- Python-окружения и зависимости — `uv`.
- Общие инструменты разработки и их версии — `mise`.
- Всё приложение и все вычислительные службы работают на одном компьютере с NVIDIA GeForce RTX 5060 Ti и **16 ГБ видеопамяти**.
- Первая версия обучения работает на одной видеокарте. Распределённое обучение не требуется.
- Конечная обученная модель должна поддерживать применение на CPU через llama.cpp.

Второй компьютер, распределённая обработка и синхронизация проектов между компьютерами не требуются. Не требовать одновременного размещения нескольких больших моделей в видеопамяти.

Для Qwen обязательно полное размещение модели и визуального модуля в GPU согласно разделу 2. Не включать автоматический перенос части весов в оперативную память.

Доступ Podman к GPU организовать через CDI NVIDIA Container Toolkit. Совместимость драйвера, CUDA и PyTorch с RTX 5060 Ti подтвердить реальным вычислением на GPU внутри контейнера. Docker не должен быть обязательной зависимостью.

Создать отдельное приложение в директории **`train-app`**, рядом с существующим каталогом `ocr`. В текущем рабочем окружении корень нового приложения — `/workspace/train-app`.

Существующий OCR-сервис не переделывать. Не изменять его исходный код, зависимости, Compose, базы данных и рабочие тома для реализации нового приложения. Миграция старых заданий не требуется.

Новое приложение имеет собственные `compose.yaml`, `pyproject.toml`, `uv.lock`, `mise.toml`, конфигурацию, данные, контейнеры и тома. Имена ресурсов Compose и порты должны позволять независимую работу с существующим OCR-сервисом. Не делать запуск зависимым от исходников или работающих контейнеров старого сервиса. При необходимости допускаются явно настроенные пути к предварительно загруженным моделям только для чтения.

Собранный интерфейс раздаёт `app` с того же адреса, что и API. В рабочем окружении отдельный сервер Node.js не нужен. Node.js требуется для сборки и разработки интерфейса; его версию фиксирует mise, зависимости JavaScript — `package.json` и `package-lock.json`, установка выполняется через `npm ci`. `uv` управляет Python, а не зависимостями браузерного интерфейса.

SVG использует систему координат сохранённого изображения. Изображение и рамки имеют одно преобразование масштаба и перемещения; не вычислять координаты рамок непосредственно из экранных размеров без обратного преобразования.

**Визуальный редактор таблиц подтверждён владельцем.** Поддержать правку текста непосредственно в отображаемой ячейке, вставку и удаление строк и столбцов, объединение и разделение ячеек. Исходный HTML оставить дополнительным режимом CodeMirror. Внутри хранить строки, ячейки и объединения с проверкой корректности; не использовать плоскую сетку с потерей `rowspan` и `colspan`. Текстовый и визуальный режимы изменяют одну редакцию, с отменой и повтором правок. Ошибочную структуру не сохранять как утверждённый эталон.

При отрисовке разрешать необходимые таблицам `rowspan`, `colspan` и переносы. Исключить сценарии, обработчики событий, внешние изображения, шрифты, стили и встраиваемые страницы. Очищенное представление для браузера не должно молча заменять исходный ответ или утверждённую обучающую разметку. Ошибочный HTML показывать с диагностикой; исправления браузера не считать утверждённым эталоном.

### 4.2. Исполнение и зависимости

В основной службе не использовать фоновые задачи FastAPI как единственное место хранения длительных операций. SQLite хранит очередь, идентификаторы попыток, состояние, прогресс и ссылки на результаты. Лёгкий диспетчер выбирает готовые задания; длительные вычисления выполняют отдельные службы. Для первой версии достаточно одного процесса API с управляемым диспетчером; разбор PDF и другие тяжёлые операции CPU выполнять вне цикла обработки HTTP с ограниченным параллелизмом.

Предусмотреть короткие транзакции и единственного владельца прикладной базы — `app`. Вычислительные службы взаимодействуют через HTTP; напрямую основную SQLite не изменяют. Прикладные исполнители, включая `trainer`, сохраняют собственный журнал операций для восстановления. Для стандартного llama-server действуют отдельные правила ниже. Базу и файлы блокировки размещать на локальной файловой системе. При выбранном масштабе одного пользователя и одной GPU Redis, Celery и PostgreSQL не требуются.

Прикладная вычислительная служба принимает операцию с устойчивым идентификатором, возвращает подтверждение приёма и предоставляет отдельные запросы состояния, результата и отмены. Не удерживать один HTTP-запрос на всё обучение. Повторная отправка того же идентификатора возвращает существующую операцию. Истечение срока аренды задания диспетчером не доказывает остановку вычислительной службы: перед повтором обязательна сверка состояния.

Контейнер Qwen содержит обычный llama-server без обязательной дополнительной службы Python. Адаптер в `app` ведёт устойчивое задание страницы и вызывает `/v1/chat/completions`; один запрос генерации может длиться до завершения этой страницы. Не приписывать llama.cpp поддержку долговечных прикладных заданий, восстановления ответа или идемпотентного запуска по нашему идентификатору. Использовать один слот и одного клиента-диспетчера. После разрыва связи проверить доступное состояние слота и не отправлять повтор, пока прежняя генерация может продолжаться. Неизвестное состояние показывать явно; при невозможности подтвердить освобождение требуется остановка и повторный запуск службы пользователем. После подтверждённого освобождения допускается новая попытка страницы; сохранённые успешные страницы не повторять. Частичный поток ответа сохранять отдельно для диагностики, не считать завершённым результатом.

Небольшие результаты сначала записывать во временный файл и атомарно переименовывать; большие наборы и контрольные точки публиковать только после записи проверяемого перечня файлов и отметки завершения. База хранит ссылку лишь на опубликованный результат. Предусмотреть восстановление после сбоя между записью файла и транзакцией базы.

Основная и вычислительные службы имеют независимые окружения Python и зафиксированные зависимости. Общие схемы данных вынести в небольшую локальную библиотеку. Для несовместимых наборов зависимостей использовать отдельные `pyproject.toml` и `uv.lock` внутри одного репозитория; не требовать установки PyTorch, CUDA и средств обучения в `app`. Применение TRL и Unsloth разрешать только после проверки совместимости с конкретным LightOnOCR и эталонным запуском Transformers/PEFT.

Разместить компоненты в одном репозитории с общей библиотекой форматов данных. Основная и вычислительные службы должны иметь независимые точки запуска.

Зависимости Python описать в соответствующих `pyproject.toml`, точные версии сохранить в `uv.lock`. Инструменты и команды разработки определить в `mise.toml`. Предоставить `compose.yaml` и зафиксировать проверенный поставщик Compose. Предлагаемый адрес нового интерфейса по умолчанию — `http://127.0.0.1:8001`; вычислительные HTTP-службы доступны внутри сети Compose. Не занимать порт существующего OCR-сервиса.

Существующий код разрешается изучать как справочный материал, но реализацию и все изменения нового приложения выполнять внутри `train-app`.

## 5. Архитектура служб

Пользователь работает с **одним приложением и одним интерфейсом**. Вычисления выполняются независимо запускаемыми службами.

| Служба Compose | Назначение | GPU |
| --- | --- | --- |
| `app` | Интерфейс, проекты, документы, результаты, очереди, проверка и наборы данных | Не требуется |
| `lighton4b` | Распознавание LightOnOCR-3-4B | Требуется |
| `qwen` | llama-server CUDA: Qwen3.8-27B Q3 и mmproj, подключение из app по API | Требуется |
| `trainer` | Обучение LightOnOCR-3-0.8B, оценка и пробное распознавание контрольными точками | Требуется |

Сравнение сохранённых результатов по возможности выполнять в основной службе, без обязательного наличия загруженной модели. Дополнительное пояснение расхождений Qwen допускается как отдельная операция.

Внутри `trainer` обучение, оценку и пробное распознавание выполнять последовательно. При смене операции освобождать память предыдущей модели, оптимизатора и промежуточных данных.

Основная служба должна запускаться без вычислительных служб и продолжать работу после их остановки. Не устанавливать в основной контейнер тяжёлые зависимости обучения без необходимости.

Создание проекта не должно создавать дополнительные вычислительные контейнеры. Службы используются совместно всеми проектами через очередь.

## 6. Запуск и обнаружение вычислительных служб

Пользователь вручную запускает и останавливает нужные службы через Compose. Предусмотреть отдельные профили и документировать команды:

```bash
podman compose up -d app

podman compose --profile lighton4b up -d lighton4b
podman compose --profile lighton4b stop lighton4b

podman compose --profile qwen up -d qwen
podman compose --profile qwen stop qwen

podman compose --profile trainer up -d trainer
podman compose --profile trainer stop trainer
```

При переключении моделей не требуется перезапускать `app`. Основная служба не должна иметь обязательных зависимостей запуска от вычислительных служб.

Не подключать сокет Podman к приложению для управления контейнерами. Приложение проверяет HTTP-интерфейсы служб; контейнерами управляет пользователь.

Для каждой вычислительной службы приложение показывает, на основании её API и собственного журнала:

- Доступность процесса.
- Готовность модели.
- Текущую операцию и идентификатор задания.
- Поддерживаемые операции.
- Загруженную модель и её версию.
- Последнюю ошибку.

Для Qwen проверять штатную готовность llama-server и доступные сведения о модели и слоте. Прикладной идентификатор задания и историю ошибок хранит `app`; не требовать этих полей от стандартного API llama.cpp и не подменять недоступные сведения предположениями.

Различать состояния: служба недоступна; модель не загружена; модель загружается; служба готова; служба занята; ожидание GPU; ошибка.

Отсутствие HTTP-ответа не считать достоверным подтверждением остановки контейнера. Показывать время последней проверки.

В интерфейсе предоставить кнопку **«Проверить службы»**. Проверять доступность также перед отправкой задания. Во время активной операции допустим ограниченный периодический опрос.

Если нужная служба недоступна, показывать её название, состояние, команду запуска и кнопку повторной проверки. Это не должно мешать просмотру и ручному редактированию сохранённых данных.

## 7. Исключительное использование GPU

На одном компьютере обеспечить согласованное исключительное использование GPU вычислительными службами. Допустимая реализация — межпроцессная блокировка через общий локальный том.

Получать блокировку до загрузки модели. Удерживать её, пока служба занимает GPU. Освобождать после выгрузки модели или завершения процесса.

Если несколько служб запущены одновременно, ожидающая служба не должна начинать загрузку модели. Она сообщает состояние ожидания освобождения GPU.

После аварии или остановки контейнера блокировка не должна оставаться навсегда. Исключить гонку между проверкой доступной памяти и фактической загрузкой.

## 9. Загрузка документов и модель данных

В первой версии поддержать PDF, PNG и JPEG. Каждое отдельно загруженное изображение считать одностраничным документом.

Поддержать загрузку **не менее 100 документов за одно действие**: выбор нескольких файлов и перетаскивание в браузер.

Передавать файлы с ограниченным параллелизмом и потоковым сохранением. Не помещать весь набор в память браузера или сервера. Показывать состояние каждого файла, позволять повторить неудачную загрузку. Ошибка одного файла не отменяет остальные.

Для документа сохранять:

- Проект, уникальный идентификатор и исходное имя.
- Исходный файл без изменений и SHA-256.
- Количество страниц и дату добавления.
- Состояние каждого этапа.
- Принадлежность к выборке и семейству шаблонов.

Обнаруживать дубликаты внутри проекта. Не перезаписывать существующие результаты при повторной загрузке.

Для страницы сохранять:

- Документ, номер и уникальный идентификатор.
- Изображение, полученное из документа до модельных преобразований.
- Размеры, разрешение и применённый поворот.
- Фактические изображения, переданные каждой модели, если они отличаются.
- Преобразования между системами координат.
- Все версии модельных ответов, сравнения и ручные редакции.

Для модельного результата сохранять исходный ответ без изменений, обработанный Markdown с HTML-таблицами, блоки и координаты, модель и её версию, точность весов, инструкцию, параметры генерации, средство исполнения, продолжительность и ошибки.

Каждое сравнение ссылается на точные версии обоих модельных ответов. Новый ответ не заменяет старый и не изменяет ручную редакцию. В интерфейсе явно показывать выбранную пару результатов и наличие более новых версий; старое сравнение не выдавать за проверку нового ответа. Утверждения и версии наборов данных ссылаются на точную редакцию аннотации и изображения.

Первичные ответы моделей неизменяемы. Новое распознавание создаёт новую версию. Ручные исправления хранятся отдельно с историей изменений.

Различать модельные предложения и утверждённые аннотации. Для каждой редакции независимо хранить состояние проверки текста и структуры таблиц, а также состояние проверки геометрии, типов блоков и их соответствия содержимому. Принятие текста не означает принятия рамок.

## 11. Массовое выполнение этапов

На уровне проекта предоставить действия:

- «Распознать через LightOn».
- «Распознать через Qwen и сравнить».
- «Открыть очередь ручной проверки».
- «Создать версию набора данных».
- «Запустить обучение».
- «Запустить оценку».

**Переход к следующему этапу всегда инициирует пользователь.** Завершение OCR, совпадение ответов моделей или запуск вычислительного контейнера не запускают следующий этап автоматически. Служба, уже поднятая в Compose, означает готовность принять запрошенную работу, а не согласие на её выполнение. Перед ручным запуском проверять необходимые данные и показывать число подходящих страниц и причины исключения остальных. Выполнение страниц внутри уже запущенного массового этапа продолжается автоматически в рамках выбранного объёма.

Для распознавания поддержать запуск по всем документам, по выделенным документам, только по необработанным страницам, только по ошибочным страницам и повторный запуск с новой версией результата.

По умолчанию не повторять успешно завершённые операции. До запуска показывать число подходящих и пропускаемых страниц с причинами.

Третий этап создаёт очередь ручной проверки; массовый запуск не означает автоматическое утверждение. Обучение запускается один раз по версии набора данных проекта, а не отдельно для каждого документа.

Массовое задание состоит из операций по документам и страницам. Показывать завершённые документы и страницы, ошибки, ожидание и текущую операцию.

## 12. Первый этап: LightOnOCR-3-4B

1. Подготовить изображения страниц.
2. Последовательно распознать страницы в режиме `grounding`.
3. Сохранить исходный ответ, текст, таблицы, блоки и рамки.
4. Предоставить результат для просмотра сразу после сохранения страницы.

Использовать стандартный однопроходный режим модели: изображение и инструкция `grounding` дают единую последовательность меток блоков, координат и содержимого. Не добавлять обязательное повторное распознавание вырезанных областей. Координаты являются частью генерируемой последовательности, а не результатом отдельного обязательного детектора.

Модель выдаёт координаты `[x_min, y_min, x_max, y_max]`, нормированные к диапазону 0–1000. Сохранять их и точную систему отсчёта; для интерфейса дополнительно вычислять координаты в пикселях сохранённого изображения. Хранить преобразования после изменения размера, поворота и вырезания области. При изменении геометрии повторно проверять соответствие координат и изображения.

Разбор должен сохранять тип, содержимое, порядок и признак продолжения блока, включая метки вроде `text+`. Неразобранное содержимое не отбрасывать молча: сохранять исходный ответ и отмечать ошибку разбора. Отсутствие корректных рамок не должно уничтожать доступный текст.

HTML-таблицы должны сохранять `rowspan`, `colspan`, пустые ячейки и переносы строк. Не преобразовывать их в плоские таблицы с потерей структуры.

Подготовку изображения сделать настраиваемой. Записывать фактические размеры входа модели и, где доступно, число визуальных токенов. Не уменьшать разрешение автоматически только ради скорости.

После первого этапа пользователь видит исходное изображение, отключаемые рамки, отрисованный текст, исходную разметку и сведения об обработке.

## 13. Второй этап: Qwen и сравнение

Первое распознавание Qwen выполняется независимо: модель получает изображение и инструкцию по формату ответа, но не ответ LightOn.

Сохранять результат Qwen всегда, даже при совпадении. Не заменять им исходный результат LightOn.

Сравнивать отдельно:

- Текст и числовые значения.
- Порядок и количество строк и столбцов.
- Объединения ячеек.
- Пропущенные и добавленные элементы.
- Отличия только в оформлении.

Структуру HTML сравнивать программно. Дополнительное объяснение Qwen допустимо, но не является единственным основанием решения.

Разрешена нормализация технических различий HTML и незначимых пробелов. Нельзя считать эквивалентными пустую ячейку и ноль, прочерк и отсутствие значения, `0012` и `12`, разные знаки чисел, разные объединения или перемещение значений между ячейками.

Результат сравнения: модели согласны; обнаружены расхождения; сравнение невозможно; ошибка распознавания. Сохранять причины и ссылки на различающиеся элементы, где их удалось сопоставить.

**Автоматическое согласие моделей не означает подтверждённую правильность.** В обучающий набор допускаются только утверждённые человеком редакции.

## 14. Третий этап: ручная проверка

Основной экран:

- Слева — исходное изображение страницы или фотография.
- Справа — отрисованный Markdown с HTML-таблицами.
- Переключатель LightOn / Qwen / окончательная редакция.
- Режим просмотра различий.
- Редактор разметки с предварительным просмотром.

Результат LightOn — не только HTML: это Markdown с HTML-таблицами и, в режиме `grounding`, специальными метками типов и координат. Разобрать этот формат и отобразить обычный текст, заголовки и таблицы средствами Markdown/HTML. Метки рамок не должны отображаться пользователю как сломанные ссылки на картинки.

Пользователь работает с понятным сценарием: выбирает ответ модели, исправляет текст или HTML-таблицу, сразу видит отрисованный результат и утверждает редакцию для обучения. Не требовать ручного составления списка блоков, редактирования JSON или числовых координат. Пространственная разметка показывается поверх изображения и редактируется графически по желанию.

Внутренний блок — фрагмент документа, например заголовок, абзац или таблица, с содержимым и необязательной рамкой. Приложение ведёт привязки между редактируемым текстом и этими фрагментами. Полная расшифровка и содержимое блоков не должны быть двумя независимо изменяемыми эталонами: это представления одной версионируемой аннотации. При неоднозначной правке полной страницы сохранять текст и явно отмечать привязки, требующие проверки, вместо потери текста или автоматического присвоения старых рамок.

Поддержать масштабирование, перемещение изображения, рамки и переход между страницами. Источник рамок обозначать явно. Не показывать координаты LightOn как координаты результата Qwen.

Добавить редактор пространственной разметки: создание, изменение размера, перемещение и удаление прямоугольников; выбор типа блока; изменение порядка чтения; привязка содержимого к блоку; обозначение продолжения предыдущего блока. Изменение порядка чтения не должно автоматически заменять его сортировкой рамок сверху вниз.

Пользователь может принять любой вариант, исправить его, сохранить черновик, утвердить, отклонить страницу как непригодную или отложить проверку.

При переключении вариантов и страниц не терять несохранённые изменения. Предусмотреть горячие клавиши, переход к следующей непроверенной странице, фильтры и сохранение положения в очереди.

Отрисовка должна сохранять объединённые ячейки, многоуровневые заголовки и переносы внутри ячеек. Запретить выполнение сценариев и загрузку внешних ресурсов из разметки.

Утверждённая редакция должна соответствовать изображению. Не исправлять числа и отсутствующие значения на основании предположений о смысле.

Предоставить два независимых действия: **«Утвердить текст и таблицы»** и **«Утвердить пространственную разметку»**. Второе означает проверку рамок, типов, порядка и соответствия содержимому блоков; оно допустимо только для текущей утверждённой текстовой редакции.

После правки текста, разбиения на блоки, выбора варианта Qwen или изменения изображения ранее утверждённую пространственную разметку отмечать как требующую повторной проверки. Сохранять историю и не изменять уже зафиксированные версии данных. Не переносить старые рамки на новую редакцию без проверки привязок.

Различать последствия пространственных правок. Перемещение рамки без изменения содержимого требует повторного утверждения геометрии, сохраняя утверждение текста. Изменение порядка чтения, состава блоков или содержимого, меняющее расшифровку, создаёт новую текстовую редакцию и снимает оба утверждения. Замена изображения требует пересмотра обоих утверждений.

## 15. Выборки внутри проекта

Через интерфейс управлять обучающей (`train`), валидационной (`validation`), тестовой (`test`) выборками и нераспределёнными документами.

Поддержать:

- Назначение выборки одному или нескольким документам.
- Автоматическое распределение с долями и случайным зерном.
- Фильтрацию и просмотр каждой выборки.
- Открытие документов, страниц, фотографий и эталонных ответов внутри выборки.
- Статистику документов, страниц, утверждённых и непригодных примеров.
- Изменение распределения для будущих версий набора данных.

Все страницы документа, его кропы и производные изображения должны оставаться в одной выборке. Дубликаты не распределять между разными выборками. Предусмотреть группировку по семействам шаблонов.

Тестовую выборку не использовать для подбора параметров. Если пользователь назначил только `train` и `test`, валидационную часть выделять из `train` по документам и фиксировать её состав. Не использовать `test` вместо валидации.

Сохранять историю использования исходных документов и их производных во всех обучающих запусках проекта. Документ, использованный для обучения модели или её исходной дообученной контрольной точки, не может считаться независимым тестом этой модели после переноса в другую выборку. Обнаруживать совпадения и подтверждённые группы похожих страниц, а не только одинаковые байты файлов. При оценке показывать и исключать такие пересечения из независимого результата; состав исключений сохранять.

## 16. Состав, экспорт и версии наборов данных

### 16.1. Основной принцип

Хранить **полную разметку страницы**, а не только текст после удаления координат. Отдельно формировать обучающие представления для обычного OCR и `grounding`.

LightOnOCR-3 поддерживает обе задачи. Наличие рамок не является обязательным условием обучения обычному OCR, но проверенные рамки, типы блоков и привязки нужны для обучения `grounding`. Модельные ответы служат предложениями для разметки, а не автоматически достоверными эталонами.

### 16.2. Обязательное содержимое аннотации страницы

| Поле | Требование |
| --- | --- |
| Проект, документ и страница | Стабильные идентификаторы и номер страницы |
| Изображение | Файл без потерь, SHA-256, ширина, высота и сведения о подготовке |
| Утверждённая расшифровка | Полный текст страницы в порядке чтения, Markdown с HTML-таблицами |
| Блоки | Стабильный идентификатор блока, содержимое, порядок, тип, рамка и признак продолжения; отсутствующая или непроверенная геометрия обозначается явно |
| Координаты | Порядок осей, единицы, изображение системы отсчёта и преобразования; поддержать представления 0–1000 и в пикселях |
| Проверка | Независимые состояния утверждения текста и пространственной разметки, проверяющий, время и версия редакции |
| Происхождение | Связь с исходными ответами LightOn и Qwen и ручными исправлениями |
| Выборка | `train`, `validation` или `test`, назначенные по исходному документу |

Поле рамки может отсутствовать в утверждённой текстовой аннотации. Такой пример пригоден для обычного OCR, но не для обучения `grounding`.

Содержимое утверждённых блоков должно быть согласовано с полной утверждённой расшифровкой. При невозможности установить соответствие разрешать экспорт обычного OCR, но запрещать экспорт `grounding` до устранения расхождений. Нельзя независимо хранить две противоречащие друг другу версии эталонного текста под одним утверждением.

### 16.3. Требования к таблицам и полноте

Эталонные HTML-таблицы должны сохранять правильные строки, столбцы, `rowspan`, `colspan`, пустые ячейки, многоуровневые заголовки, переносы, точные числа, знаки, ведущие нули и единицы измерения.

Рамка всей таблицы не заменяет её HTML-структуру. Разметка координат каждой ячейки не обязательна для стандартного формата LightOnOCR-3 и не должна становиться условием подготовки первой версии данных.

Полной странице соответствует полный ответ, включая видимые заголовки, колонтитулы, номера страниц и примечания. Не применять скрытое удаление элементов ради показателей оценки. Для отдельной таблицы использовать изображение этой таблицы и соответствующий ответ; сохранять связь с исходной страницей и преобразование координат.

Сохранять содержимое графиков, иллюстраций и их описаний с явным типом блока. При формировании ответа применять зафиксированные правила, соответствующие выбранному режиму LightOn; не смешивать описание изображения с буквальной расшифровкой печатного текста без обозначения его происхождения.

Неполные, обрезанные, повторяющиеся или неоднозначно размеченные ответы не допускать как готовые эталоны. Реально пустая страница может быть самостоятельным проверенным примером с пустым содержательным ответом и корректным завершением последовательности.

### 16.4. Обучающее представление обычного OCR

```text
Вход: изображение без текстовой инструкции.
Ответ: полная проверенная расшифровка страницы в Markdown с HTML-таблицами.
Метки координат и типов блоков отсутствуют.
```

Допускать только текущие редакции с утверждённым текстом и структурой таблиц. Проверка рамок для этого представления не обязательна.

При преобразовании результата `grounding` использовать разбор блоков, порядок чтения и признаки продолжения. Удалять только служебные метки; не удалять обычную Markdown-разметку и содержимое. Само удаление меток из непроверенного ответа не делает его эталоном.

### 16.5. Обучающее представление `grounding`

```text
Вход: изображение и инструкция grounding.
Ответ: последовательность проверенных блоков вида
![тип](x_min,y_min,x_max,y_max)
содержимое блока
Координаты нормированы к диапазону 0–1000.
```

Допускать только редакции с утверждённым текстом и утверждённой пространственной разметкой той же версии. Проверять диапазоны и ориентацию прямоугольников, типы, полноту, порядок, признаки продолжения, отсутствие дубликатов и соответствие текста областям. Сохранять правила округления координат и обработки границ.

Не экспортировать проверенный текст вместе с непроверенными рамками. Не использовать другое координатное представление или формат локализации LightOnOCR-2 как целевой формат LightOnOCR-3.

### 16.6. Версионирование и состав экспорта

Версия набора данных неизменяема. Сохранять исходные аннотации и сформированные примеры: изображения, оба доступных обучающих представления, выборки, происхождение, состояния проверки, контрольные суммы и версию преобразования.

Предоставить сведения о числе уникальных страниц, примеров обычного OCR и примеров `grounding` отдельно. Два представления одной страницы не считать двумя независимыми страницами и всегда помещать в одну выборку вместе с её производными изображениями.

Изменения проекта не должны менять существующую версию или действующее обучение. Сохранять связь каждой ошибки оценки с исходной страницей и версией эталона. Параметры подготовки изображений для обучаемой модели фиксировать отдельно от параметров модели, подготовившей предложения.

## 17. Четвёртый этап: обучение LightOnOCR-3-0.8B

Обучать оригинальные веса Hugging Face, а не GGUF.

Начальная экономная конфигурация для контрольного эксперимента ориентирована на одну RTX 5060 Ti 16 ГБ. Она не объявляется заранее оптимальной по качеству:

- LoRA в текстовом декодере.
- Замороженные визуальный энкодер и модуль объединения признаков.
- BF16 при подтверждённой поддержке.
- Размер пакета 1.
- Накопление градиентов.
- Повторное вычисление промежуточных активаций для экономии памяти.

Проверить состав модулей Qwen3.5. Не переносить непроверенный список целей LoRA от другой архитектуры. Сохранять полный перечень и количество обучаемых параметров.

Предусмотреть отдельный эксперимент с LoRA в декодере и визуальной части, включая проверку состояния модуля объединения признаков. Состав обучаемых частей выбирается явно. Замороженный энкодер не должен быть жёстким ограничением архитектуры приложения. Полное дообучение допускается как дополнительный эксперимент при фактически подтверждённой вместимости, но не является обязательным условием запуска на 16 ГБ и не гарантирует улучшения.

Применять Unsloth только после проверки совместимости именно с исходным checkpoint LightOnOCR-3-0.8B, его обработчиком изображений и шаблоном диалога. Поддержка базового Qwen3.5 сама по себе недостаточна. Предусмотреть эталонный путь через Transformers и PEFT для проверки подготовки данных и результатов. Выбор средства обучения не должен менять формат целевой задачи.

Поддержать два явно выбираемых режима запуска: обучение обычному OCR и смешанное обучение обычному OCR и `grounding`. В смешанном режиме долю задач задавать конфигурацией и сохранять фактическое число выборок каждой задачи. Не подменять один режим другим при отсутствии данных: показать причину и предложить выбрать допустимый режим.

Для первого смешанного эксперимента допустима отправная пропорция 80% обычного OCR и 20% `grounding`, только если есть достаточно проверенной пространственной разметки. Это настраиваемая гипотеза, а не гарантированный оптимум и не требование копировать исходное обучение авторов. Повторная выборка одних и тех же страниц не увеличивает число независимых примеров.

Сравнить исходную модель, обучение только OCR и смешанное обучение на одной зафиксированной версии данных. Выбирать режим и контрольную точку по валидации; независимую тестовую выборку использовать для итогового отчёта. При недостатке данных для одного из сравнений явно указать ограничение.

Обязательные проверки:

- Ошибка вычисляется только по ответу ассистента.
- Входное изображение и инструкция не входят в обучающую цель.
- Корректно размечено завершение ответа.
- Режим размышлений отключён.
- Изображения, визуальные токены и окончания таблиц не обрезаются молча.
- Подготовка изображений согласована с последующим применением.
- Для распознавания корректно включено использование доступного кэша состояний.

Использовать `AutoProcessor` и соответствующий класс Qwen3.5 из зафиксированной совместимой версии Transformers. Не использовать классы `LightOnOcrProcessor` и `LightOnOcrForConditionalGeneration` предыдущих поколений для checkpoint третьего поколения на Qwen3.5.

Формировать полную последовательность и входной префикс штатным шаблоном выбранной версии модели с `enable_thinking=False`. Не искать начало ответа по скопированным из старых примеров числовым идентификаторам. Определять границу через поддерживаемую маску шаблона либо совпадающий токенизированный префикс; обязательно проверять фактическое совпадение префикса после разворачивания визуальных токенов. При несовпадении завершать подготовку с диагностикой, а не обучать на предположительной границе.

Для каждого типа примера декодировать немаскированную часть целей и проверять, что она равна эталонному ответу с корректным завершением. Не включать в ошибку входные, визуальные и добавленные для выравнивания токены. Для непустого эталона запрещён нулевой набор целевых токенов. Пустой служебный блок размышлений в шаблоне не считать содержательным ответом. Завершающий токен определять по токенизатору конкретной модели; не путать его с токеном выравнивания.

В примерах `grounding` координаты и типы блоков являются частью ответа ассистента и входят в ошибку обучения вместе с содержимым. Их нельзя маскировать как инструкцию. Режим размышлений, шаблон диалога и инструкция задачи должны соответствовать формируемому примеру. Отдельная функция ошибки детектора и обучение с подкреплением не требуются для первой версии LoRA-обучения.

До длительного обучения выполнить короткую проверку, включая самые длинные примеры, и измерить расход памяти. Разрешение автоматически не снижать. При нехватке памяти завершать операцию с диагностикой и сохранять её конфигурацию.

Через интерфейс пользователь выбирает проект, версию данных и параметры, запускает и останавливает обучение, просматривает журнал и показатели, выбирает контрольные точки и продолжает совместимый незавершённый запуск.

Сохранять исходную модель, версию данных, конфигурацию, версии библиотек, случайное зерно, журнал, состояние оптимизатора и прочие данные, необходимые для продолжения, адаптеры и контрольные точки. Различать контрольную точку для продолжения обучения и модель для распознавания.

## 18. Оценка дообучения и пробное распознавание

### 18.1. Обязательный рабочий процесс

Оценка — часть того же приложения и процесса обучения. Через интерфейс пользователь выбирает версию данных, выборку и контрольную точку, запускает оценку и получает сравнение исходной и обученной LightOnOCR-3-0.8B. Не ограничиваться сообщением об успешном завершении обучения или значением ошибки на обучающих примерах.

Во время обучения использовать валидационную выборку для выбора контрольных точек, параметров и ранней остановки. После выбора выполнить сравнение на независимой тестовой выборке. Не менять эталоны под полученные ответы. Если по результатам теста подбирались параметры следующего обучения, не представлять тот же набор как ранее не использованный: сохранять историю оценок и предупреждать о снижении независимости.

Для каждой пары моделей использовать одни и те же страницы, эталоны, подготовку изображения и согласованные настройки генерации. Фиксировать версии модели, процессора, токенизатора, оценщика, нормализации, параметры и случайное зерно. Оценивать свободную генерацию полного ответа без передачи правильного ответа модели.

Приложение должно показывать улучшение, отсутствие улучшения и ухудшение. Не скрывать неудачные запуски и не объявлять любые завершившиеся веса лучшими. Решение об использовании конкретной модели остаётся за пользователем на основании автоматического отчёта и, по желанию, личной проверки.

### 18.2. Показатели текста и таблиц

| Показатель | Что измерять |
| --- | --- |
| CER | Число замен, удалений и вставок символов, делённое на длину эталона; меньше — лучше |
| TEDS | Сходство структуры HTML-таблицы с учётом содержимого ячеек; больше — лучше |
| TEDS-Struct | Сходство структуры таблицы без содержимого ячеек, включая объединения |
| Точное совпадение числовых ячеек | Совпадение полных строк значений на правильных местах, с учётом знаков, ведущих нулей и разделителей |
| Доля полностью правильных таблиц | Совпадение структуры и содержимого всех ячеек после допустимой технической нормализации |
| Пропущенные и лишние элементы | Таблицы, строки, столбцы, ячейки и содержательные блоки |
| Некорректные ответы | Ошибки распознавания, пустые ответы на непустых страницах, некорректная разметка и обрезанные результаты |
| Скорость и память | Полное время страницы, время этапов и пиковая память при одинаковых условиях |

Не сводить результат к одному среднему баллу. Высокий TEDS не означает отсутствие ошибок в числах. Для числовых ячеек показывать отдельно долю правильных эталонных ячеек и лишние предсказанные значения: пропущенная ячейка не исчезает из знаменателя, а совпавшее значение в другом месте не считается правильным.

Для CER отделять видимый текст от служебной Markdown/HTML-разметки по общим правилам. Фиксировать допустимую нормализацию Unicode, пробелов и переносов. Не заменять автоматически кириллицу латиницей, `ё` на `е`, ноль буквой, не убирать значащие знаки и не приводить номера с ведущими нулями к числам. CER может превышать 100% при множественных вставках. Пустые эталоны учитывать отдельной проверкой лишнего сгенерированного содержимого, без деления на ноль.

TEDS и TEDS-Struct вычислять зафиксированной проверенной реализацией. Подготовку HTML документировать и проверять на `th`, `td`, `rowspan`, `colspan`, пустых ячейках и переносах. Различие только технического оформления допустимо нормализовать; содержательные различия нельзя исправлять оценщиком.

Учитывать особенности исходного оценщика PubTabNet: он принимает одну пару таблиц, выбирает первую таблицу из HTML и специально обрабатывает содержимое `td`. Поэтому перед расчётом выделять каждую таблицу отдельно и приводить вход к проверенному совместимому представлению в копии для оценщика, включая обработку `th` без потери текста и объединений. Исходные эталоны не перезаписывать.

### 18.3. Сопоставление и полнота оценки

До вычисления показателей сопоставить таблицы страницы, затем строки и ячейки с учётом структуры и порядка. В `grounding` доступна дополнительная геометрия. Не сопоставлять ячейки произвольным поиском одинаковых чисел по всей странице. Правила выравнивания, обработки пропущенной строки, разных объединений и разделения таблицы должны быть описаны и зафиксированы примерами ожидаемого поведения.

Перед запуском проверять разбор и полноту эталонов. Ошибка эталона останавливает соответствующий расчёт с диагностикой, а не считается ошибкой модели и не исключается молча. Незавершённую оценку нельзя показывать как полный результат по всей выборке.

Каждая тестовая страница входит в отчёт. Пропущенные таблицы, ошибки разбора, нехватка памяти и тайм-ауты не должны исключаться так, чтобы повышать итоговые показатели. Для применимой эталонной таблицы отсутствующий результат учитывается как нулевое качество таблицы; лишние таблицы отражаются отдельным показателем. Ошибка самого оценщика отмечается отдельно от ошибки модели, не выдаётся за качественную оценку и не скрывается.

Сохранять сопоставления, исходные ответы и причины штрафов, чтобы пользователь мог открыть конкретную ошибку. Показатели показывать по страницам, документам и категориям сложности. Указывать число документов, страниц и таблиц, распределение результатов, а не только общий средний балл. Метод усреднения фиксировать. Если рассчитывается неопределённость разницы моделей, учитывать зависимость страниц одного документа, например повторной выборкой целых документов.

Из утверждённых эталонов можно дополнительно формировать проверяемые условия: значение находится под нужным заголовком, итоговая строка сохранена, единицы измерения не потеряны, соседние строки не переставлены. Такие проверки дополняют полную оценку. Не переносить условия чужого набора, требующие удаления колонтитулов, если наша цель — весь видимый текст страницы.

### 18.4. Пространственная разметка и контроль ухудшений

Обычный OCR и `grounding` оценивать отдельно, с соответствующими инструкциями. Для извлечения текста из `grounding` применять один и тот же зафиксированный разбор ко всем моделям.

На подмножестве с утверждённой геометрией показывать IoU, точность и полноту обнаружения блоков, правильность типов и порядка чтения. Описать правила однозначного сопоставления и пороги пересечения. Не использовать непроверенные рамки LightOnOCR-3-4B как истинную разметку. При отсутствии геометрических эталонов явно показывать, что показатель не оценивался.

Помимо сложных таблиц оценивать обычный русский текст, чтобы обнаруживать ухудшение общих возможностей. Сравнивать качество до и после объединения LoRA, экспорта и Q4_K_M. Сохранять все варианты, не заменять лучший результат автоматически последним.

### 18.5. Личная проверка пользователем

Пользователь может выбрать исходную модель или любую совместимую контрольную точку, загрузить свой PDF либо изображение и выполнить распознавание в обычном режиме или `grounding`. Это необязательная личная проверка, доступная в том же интерфейсе, а не замена обязательной тестовой оценки.

Показывать исходное изображение, отрисованный ответ, исходную разметку и доступные рамки. Предусмотреть сравнение двух моделей на одном документе. Без утверждённого эталона не придумывать числовую оценку качества по мнению другой модели. Пользователь может сохранить заметку и при желании начать отдельную ручную разметку; ответ автоматически эталоном не становится.

При переключении контрольной точки не держать несколько моделей одновременно в GPU. Не начинать распознавание во время обучения на той же видеокарте.

## 19. Экспорт модели

Поддержать последовательность:

```text
LightOnOCR-3-0.8B и адаптер LoRA

→ проверка исходной точности
→ экспорт GGUF
→ квантизация Q4_K_M
```

Сохранять исходную точность и Q4_K_M отдельно. Если визуальная часть не менялась, допустим совместимый исходный визуальный модуль. Если менялась — экспортировать соответствующий модуль той же контрольной точки.

## 20. Очереди, отмена и восстановление

Состояние каждого этапа хранить отдельно. Не сводить весь документ к единственному признаку готовности.

Предусмотреть отмену массового задания, повтор страницы, продолжение после перезапуска и удаление завершённых, ошибочных или отменённых заданий.

Остановка вычислительной службы не должна удалять результаты, завершать `app`, помечать все оставшиеся страницы ошибочными, блокировать ручную работу или оставлять задание навсегда выполняющимся.

При потере связи состояние текущей операции сначала считать неизвестным: недоступная по HTTP служба может продолжать вычисление. Сохранять идентификаторы операции и попытки, сверять их состояние после восстановления связи и не создавать вторую такую же операцию без проверки. Подтверждённо завершившуюся без результата операцию отметить как прерванную, оставшиеся — как ожидающие. После восстановления продолжать задание без повторения сохранённых успешных страниц, если пользователь его не отменил.

Сохранять результаты атомарно. Повторная доставка операции не должна создавать дубликаты или повреждать данные. Ответ на отменённую либо устаревшую операцию не должен перезаписывать новую редакцию или результат другого запуска.

Различать штатную остановку обучения через интерфейс и аварийное завершение контейнера. При штатной остановке закончить текущий шаг, сохранить полную контрольную точку и только после этого подтвердить остановку; показывать состояние сохранения. При аварии допускается потеря шагов после последней целой контрольной точки. Интервал сохранения задаётся в конфигурации; интерфейс показывает последний сохранённый шаг. Неполные контрольные точки не предлагать для продолжения или распознавания. Остановка контейнера не гарантирует сохранения текущего шага.

Ошибка одной страницы не останавливает остальные. Исключить бесконечные повторы и обращения к завершившемуся процессу модели без восстановления исполнителя.

Для тяжёлых заданий разных проектов использовать общую очередь GPU. Отмена задания одного проекта не должна отменять задания другого.

Если GPU удерживает неактивная, но загруженная модель другой службы, показывать, какую службу требуется остановить и какой командой. Не отображать ожидание как выполнение. Задания для выключенной службы не должны препятствовать запуску готовых заданий доступной службы. Автоматическая остановка контейнеров не требуется.

## 24. Критерии готовности

Проверить следующий сквозной сценарий:

12. Выбрать контрольную точку и распознать новый PDF либо изображение.
13. Остановить `trainer`; убедиться, что все результаты доступны.

Для подготовки данных дополнительно проверить, что утверждённый текст с непроверенными рамками экспортируется только в обычный OCR; исправление текста отменяет актуальность утверждения геометрии; продолжения блоков и объединения ячеек сохраняются; оба представления страницы остаются в одной выборке; при смешанном обучении метки и координаты входят в целевой ответ. Проверить качество обоих режимов после обучения и после квантизации.

Для каждого этапа явно указать, что проверено реальными моделями и оборудованием, а что осталось неподтверждённым. Проверки с подставными ответами не выдавать за подтверждение реального распознавания, вместимости в видеопамяти или обучения.

## 26. Порядок получения качественного результата

### 26.1. Подтверждённые сведения и границы применимости

Различать описание исходного обучения авторов и предлагаемые эксперименты проекта. Авторы сообщают о повышенной частоте выборки таблиц, совместных задачах OCR и `grounding`, визуальных преобразованиях, Muon и объединении примеров в контекст при обучении с учителем. Последующий этап обучения с подкреплением использует отдельную схему GRPO и усреднение моделей разных запусков. Это не готовая инструкция по LoRA на одной RTX 5060 Ti.

Не копировать автоматически оптимизатор, объединение последовательностей, доли задач, усреднение весов и обучение с подкреплением только ради формального сходства с исходным обучением. Их необходимость и корректность зависят от выбранного способа адаптации и проверяются отдельно. В частности, не усреднять адаптеры или веса произвольных запусков без отдельной проверки совместимости и качества.

Исходной точкой остаётся опубликованный LightOnOCR-3-0.8B. Не заменять его обычным Qwen3.5-0.8B или несуществующей в конфигурации промежуточной версией. Если появится официальный checkpoint до обучения с подкреплением, сравнить его отдельно, сохранив происхождение и версию.

### 26.2. Подготовка изображений

Хранить исходное изображение высокого качества отдельно от производного изображения для модели. Установить явный профиль изменения размера с сохранением пропорций. Начальная проверяемая отправная точка — длинная сторона 2048 пикселя из карточки и официального клиента, а не уменьшение до 300–1000 пикселей из общих примеров обучения.

Не считать эту отправную точку доказанным пределом качества. Для плотных таблиц сравнить достаточность выбранного разрешения и более высокого бюджета изображения на валидации при доступной памяти. В отчёте различать профиль карточки модели и более высокий профиль оценки из описания авторов. Не объявлять разрешение оценки разрешением исходного обучения без подтверждения.

Проверять результат штатного обработчика: фактические размеры, визуальную сетку, число визуальных токенов и полную длину последовательности. Параметры `size.shortest_edge` и `size.longest_edge` обработчика Qwen2-VL задают бюджеты площади в пикселях, а не длину стороны. Не передавать туда значение 2048 в предположении, что это длинная сторона. Учитывать округление к сетке патчей.

Сохранять исходную нормализацию checkpoint; в опубликованном обработчике среднее и стандартное отклонение равны 0.5 по каждому каналу. Проверять, что обёртка обучения не заменяет нормализацию и скрыто не уменьшает изображения. Профили подготовки модели, предложившей разметку, и обучаемой модели могут отличаться, но эталон должен оставаться читаемым и геометрически согласованным с фактическим входом обучаемой модели.

Максимальную длину выбирать по измеренным визуальным и текстовым токенам. Нельзя молча обрезать длинную таблицу, чтобы она поместилась в стандартные 2048 или 4096 токенов из учебного примера.

### 26.3. Качество эталонов и преобразования

Начать с проверки характерных ошибок исходной 0.8B на зафиксированной валидационной выборке. Большая модель подготовки данных не считается безошибочным эталоном: каждое содержательное исправление должно подтверждаться изображением.

Разделять проверку структуры таблицы и текста ячеек. Наличие синтаксически корректного HTML не доказывает правильность данных. Для числовых столбцов, пустых ячеек и объединений обеспечить отдельную проверку. Долю сложных примеров, обычных страниц и проверенных пустых страниц фиксировать и выбирать по валидации, а не по количеству автоматически полученных ответов.

Синтетические примеры и преобразованные копии допустимы как дополнение, а не замена реальным документам. Сначала разделять исходные документы по выборкам, затем создавать их производные. Геометрические преобразования обязаны преобразовывать рамки и при необходимости порядок; при неподтверждённом преобразовании исключать пример `grounding`. Визуальные искажения не должны делать эталон неразличимым или менять значения символов.

### 26.4. Контрольный запуск до основного обучения

Перед длительным запуском проверять:

1. Распознавание исходного checkpoint эталонным путём и выбранной обёрткой при согласованных настройках, включая оба режима.
2. Равенство входного префикса обучения и соответствующего входа распознавания, кроме целевого ответа.
3. Правильность маски и декодирование целей на обычном тексте, длинной таблице, `grounding`, продолжении блока и пустой странице, включая разную длину примеров в пакете.
4. Ненулевые конечные градиенты у выбранных обучаемых частей и отсутствие обучения замороженных частей; отсутствие нечисловых значений и повреждения модели при сохранении.
5. Способность дообучиться на небольшом отладочном наборе и воспроизвести его ответы; этот результат не считать оценкой обобщения.
6. Сохранение, повторную загрузку и генерацию из полученной контрольной точки.

Если проверка обёртки Unsloth не проходит, не продолжать длительное обучение. Использовать подтверждённый путь Transformers и PEFT либо исправить адаптацию и повторить проверку. Ускорение и расход памяти не заменяют подтверждения правильности.

### 26.5. Выбор способа адаптации

Сравнивать экономный вариант LoRA декодера и вариант LoRA с визуальной частью на одинаковых данных. Полное обучение рассматривать только при достаточной памяти и обоснованной необходимости. Для визуальной части допускаются отдельные параметры шага обучения; их значения, ранг адаптеров и длительность подбирать по валидации.

Не заявлять, что фиксированный ранг, скорость обучения, число эпох или замороженный энкодер гарантируют максимальное качество. Выбирать контрольную точку по полноценной генерации на новых документах и сохранению обоих режимов; не только по убыванию ошибки обучения. Проверять повторяемость перспективного варианта на нескольких случайных зернах по мере доступного времени.

Последовательно сравнивать: исходную модель; адаптацию только OCR; смешанную адаптацию; выбранный способ изменения обучаемых частей. Не менять одновременно все параметры без возможности определить причину улучшения или ухудшения.

### 26.6. Условия принятия результата

До обучения определить целевые показатели и допустимые ухудшения на контрольном обычном тексте и `grounding`. Требования задаются конфигурацией проекта, а не подгоняются под полученный результат.

Итоговый отчёт должен показывать исходное и полученное качество, распределение ошибок, фактическое разрешение, режим, число независимых документов и страниц, параметры и расход памяти. Отсутствие разметки для показателя обозначать как отсутствие оценки, а не нулевую ошибку. При малом тестовом наборе указывать его размер и неопределённость оценки.

После выбора на валидации выполнить итоговую оценку на отложенных документах и повторить её после объединения LoRA, экспорта и квантизации. Сохранять также вариант исходной точности: снижение качества Q4_K_M не должно приводить к потере лучшей модели.
